# Architecture

## Modules and boundaries

- App Router server components read explicit data projections. Interactive forms call same-origin JSON routes.
- `/api/auth/*`: Better Auth email/password sessions; public registration disabled. Accounts provisioned by an admin or secure CLI.
- `/api/catalog`, `/api/settings/public`: public safe projections, no costs/customer data.
- `/api/referrals`: verifies active codes and sets signed, HttpOnly attribution cookie; direct visits preserve the previous code until expiry.
- `/api/orders`: public validated checkout with idempotency and stock reservations, database persistence before WhatsApp URL generation.

The WhatsApp handoff formats the persisted order into Azerbaijani sections with WhatsApp bold markers and emoji: current configured store name, reference, numbered products with selected nonstandard variants, quantities/unit and line prices, subtotal, actual snapshotted delivery fee (zero is Ödənişsiz), total, contact/address, and optional notes/referral. It uses retail order snapshots and the shared AZN formatter; purchase costs, margins and commissions are excluded. Generating/opening the encoded URL does not send a message or confirm payment/delivery.

The order response includes the original Unicode message alongside the existing encoded link (the same content, no additional private fields). On desktop the client builds a direct web.whatsapp.com/send URL from that message to bypass the wa.me redirect, which was independently observed replacing emoji with U+FFFD. Phone/iPad clients retain their existing app link; older API responses can supply the message through their encoded URL. The confirmation link and automatic popup share the chosen destination. A copy button writes the original text without URI roundtrips; a collapsible read-only preview supports review/manual copying if clipboard permission is denied. These actions never create another order or alter its status. Actual WhatsApp sending remains the customer's action.

Checkout contact fields use localized inline errors, accessible labels/descriptions and first-invalid focus. The phone control shows a fixed +994 prefix with national digits only; recognized local/international Azerbaijani formatting is normalized to +994 plus nine digits on both client and server. Arbitrary symbols, letters, foreign prefixes and invalid lengths are rejected for checkout only; generic administrator/partner phone rules remain unchanged. This validates format, not phone ownership or reachability. Client required-field and privacy-consent checks run before opening a popup or posting an order. Server field errors map back to inputs; network/non-JSON failures close the temporary popup and retain the cart. An in-memory attempt keeps the same idempotency key if session storage is blocked. Equivalent legacy local-phone request hashes can still retry an existing order without rewriting its phone/history or reserving stock twice.
- `/api/admin/*`: role-checked product/category/inventory/order/partner/commission/payout/expense/settings/dispute operations, reports and uploads.
- `/api/admin/product-trash`: bounded administrator-only, same-origin POST with explicit delete/restore action and up to 100 distinct product IDs. Serializable, audited status transitions use `DELETED` to retain variants, images, orders, payments and inventory history. Default product/inventory lists, category counts and current product exports exclude deleted products; `/admin/products?view=deleted` exposes the administrator's trash and restore controls. Existing public queries and checkout require `PUBLISHED`, so deletion also removes storefront access and public product-media authorization. Restore always returns to `DRAFT`. Stale product forms, bulk status updates, inventory adjustments and photo imports cannot reactivate or modify deleted products. Existing orders can still be processed or canceled. SKU/slug uniqueness is retained, and CSV conflicts point administrators to restore rather than duplicating business history.
- `/api/admin/product-import`: bounded JSON carrying UTF-8 CSV, administrator-only preview and explicit import. At most 200 rows/512 KiB; existing categories, SKUs and slugs are rechecked at commit. Imports create drafts with grouped variants, inventory movements and per-product audits in one serializable transaction. An actor-scoped deterministic audit receipt makes retries idempotent; it is committed atomically with products and rejects changed payloads under the same key. Existing products and reserved stock are never updated by this endpoint. The Birmarket extension's existing Full CSV is accepted, including optional `image_urls`; source price/cost/stock are never substituted for owner values. Photos-only preview resolves existing products by SKU without requiring financial fields.
- `/api/admin/product-import-photo`: administrator-only, same-origin, rate-limited request for one SKU/image URL. Exact HTTPS Birmarket and Temu CDN hosts and product-image paths are validated before fetching and at each manual redirect. Temu accepts product paths on `img.kwcdn.com`, `img-1.kwcdn.com`, `img-eu.kwcdn.com` and `img-us.kwcdn.com`; arbitrary subdomains, non-product/static assets and SVG are rejected. Downloads have a 15-second deadline, two-redirect limit and 4 MiB streamed byte bound; Sharp validates/reencodes the bytes before private Blob/S3 storage. A nullable per-product unique source-URL hash makes retries idempotent across variant SKUs. Serializable attachment enforces the 12-photo limit and commits its provider-specific audit together; unused newly uploaded objects are cleaned up after failures when they are confirmed unreferenced. Download/storage happens outside the transaction. The browser runs requests sequentially, shows progress/failures and can retry failed photos or resume with photos-only CSV. Completed metadata imports and successful photos survive individual image failures. Public images still use the existing safe catalog projection and authorized media route. Image import does not change status, price, cost, stock or reservations.

The combined browser exporter 1.1.0 keeps Birmarket's existing collection IDs and `products` storage key; Temu identities use `temu-<goods ID>` and default `TM-` SKUs/slugs with a Temu prefix. Full CSV accepts both the legacy `source_price_azn` and generic `source_price`/`source_currency` metadata without mapping them into owner AZN values. Manual Temu capture runs in the page MAIN world to read only goods-ID-matched state, structured product data or matching gallery/DOM data; scripts are never evaluated and cookies/account storage are not read. Saved product URLs remove tracking/session parameters. The manifest adds only exact Temu host permissions to the existing Birmarket permissions. The installed extension must be updated in its original folder to retain Chrome's installation identity; native extension APIs and logged-in Temu layouts require owner verification, separate from adapter/fixture tests and the verified real CDN-image pipeline.
- `/api/partner/*`: session partner ID only, never caller-supplied ownership. Own redacted orders, commission/payout/adjustment history and disputes.
- `/api/cards/*`: authorized owner/admin QR and PDF downloads.
- `/api/jobs/sync`: bearer-authenticated retry worker for a durable Google Sheets outbox.

## Roles and privacy

Product presentation now includes a public short description and a private administrator price-review flag. `ProductSlugAlias` retains previous slugs by product ID; the Node Proxy issues 301 redirects only to published products and preserves query parameters. Aliases resolve to the current slug, avoiding rename chains. Product edits, CSV creation and reviewed content releases serialize current/former slug reservation with the same advisory lock. A deleted product retains its URLs and history without redirecting visitors to private data.

Delivery uses one client/server rule: explicit configured free regions or a positive free-delivery threshold cost zero, otherwise the configured flat fee applies. The server checks the configured destination and snapshots the resulting charge on the order. Delivery-policy edits never recalculate historical fees. Business name/VÖEN/address and delivery duration/free destinations are editable settings; blank legal fields stay blank rather than fabricating business identity.

The reviewed `2026-11-07-content.json` release is scoped to this owner's branding receipt and 22 captured existing products. It translates presentation fields/image alt text, retains old URL aliases, flags the unchanged suspect sunshade price, and applies the explicitly approved delivery fields in one audited, hash-bound, serializable transaction. Conflicting newer fields abort for review; repeat runs preserve later owner edits. Deploy generic alias support before enabling the content-release preparation step, so earlier public URLs continue working while the next build updates the database.

Website branding remains database-driven through the existing store name, logo and favicon fields. `BrandLogo` uses the approved full image on light surfaces; dark surfaces use the matching favicon symbol and a readable text wordmark. Stores with a full logo but no symbol receive a light backing on dark surfaces, and unconfigured stores retain the existing fallback. Header, footer, login, admin and partner layouts share this component. Page titles/Open Graph, browser icon and printed cards continue to read store settings.

The owner-approved `branding/furycar/release.json` is a one-time, hash-bound brand update run after catalog preparation on the guarded primary target. It requires this owner's existing catalog receipt, compares the captured name/domain/logo/favicon before writing, validates and privately uploads the two assets, and changes only name/logo/favicon in one audited, advisory-locked transaction. Other installations skip it; conflicting owner edits abort for review. Replays preserve later settings edits. Domain/contact/commission/inventory/account data are not changed, original objects are retained, and unreferenced newly uploaded assets are cleaned up cautiously.

Better Auth User/Session/Account/Verification tables hold authentication. ADMIN is provisioned only by trusted CLI or the opt-in first-admin release script using private `ADMIN_EMAIL` and `ADMIN_PASSWORD`. The release step is serialized and transactional, preserves an existing administrator, rejects email collisions without promoting users, and never resets passwords. No public signup/bootstrap endpoint exists. PARTNER is linked one-to-one to a partner profile. Every protected handler and layout checks server sessions. Customer checkout is anonymous. Partner projections exclude customer identity, order addresses, phone, purchase cost and store profits. Admin financial APIs are never public.

Owned `ProductVariant.storeSku` values are allocated as FC-0001 by a transactional counter under the product/CSV namespace lock. The original `sku` stays private for supplier CSV/photo matching. Public catalog/JSON-LD use owned codes; new order snapshots prefer the owned code and past snapshots are immutable. `/api/catalog/quote` exposes only bounded published active variants and current retail/cart metadata; the device cart refreshes prices/limits without becoming a server-persisted cart.

Public navigation uses StoreLink with viewport-triggered Next.js prefetch disabled: dynamic menus/cards otherwise create many background RSC requests and database reads before a visitor chooses a product. Hover or keyboard focus restores the normal automatic/partial prefetch for the intended link, without forcing a cached full dynamic product response. Ordinary client navigation, native anchor behavior, filters/pagination and real301history remain. The navigation/filter category list shares one React-cached promise within its server render. There is no cross-request category/settings/price/stock cache; subsequent requests still see administrator edits and current availability.

`stockVerified` retains an administrator's physical count attestation as inventory metadata. At the owner's request, storefront availability now uses unreserved recorded units for every product: positive availability shows Stokda/InStock, and zero or fully reserved stock shows Stokda yoxdur/OutOfStock. There is no customer-facing verification warning. Count changes without explicit verification still invalidate the private attestation; a zero-delta verification is audited without a fabricated stock movement. Checkout checks the same unreserved recorded units and the merchant confirms actual fulfillment via WhatsApp.

The owner explicitly confirmed availability of every currently sold product on 2026-11-08. The bounded `2026-11-08-delivery-stock.json` release verifies only its captured active published variants with positive unreserved counts; prices, recorded counts, reservations and inventory movements are retained. It requires the existing owner-review receipt, rejects changed identities, nonpublished products, unavailable stock or conflicting delivery settings, and records a hash-bound receipt plus zero-delta verification audits atomically. Replays preserve later owner edits, and unrelated/preview installations skip it. The announcement is derived from the configured free regions. A shared delivery message also appears in the footer, trust row, delivery section, product, cart, checkout and terms; actual destination fees continue to use the existing client/server delivery rule.

The owner removed the rights-review workflow on 2026-11-08. Product forms have no review checkbox or clearance field, and single/bulk publication needs no clearance reference. Catalog, checkout, media and slug redirects use the chosen product status and active/available variants; retired review metadata has no operational effect. Existing drafts keep their status until an administrator publishes them. The old database columns and historical plan hashes/receipts are retained for compatibility and history; cached old form fields are ignored, and saves clear the obsolete flag while preserving previous notes. The guarded historical catalog correction still applies the explicit sunshade price/delivery-note correction and SKU backfill, but never creates new review holds or changes marked-product statuses.

## Money, orders and inventory

Catalog presentation uses contained square product images and equal-height two-line titles/price rows. Administrators can select an existing gallery image as the cover through the authenticated, same-origin `cover` image action; it verifies product ownership and non-deleted status, reorders positions transactionally and records an audit. CSV preview now shows the first pending image alongside names/categories before import.

The owner-approved `catalog/curation/2026-11-06.json` is a bounded one-time data import for 18 captured published products, not a seed or runtime catalog override. Primary Vercel preparation runs `scripts/apply-catalog-presentation.ts` after normal schema/account setup. It skips unrelated installations, rejects changed names/categories/gallery order before writes, validates asset hashes and private uploads, and commits title/category/cover changes with per-product audits and a hash-bound receipt under an advisory lock. Repeated builds do not overwrite later owner edits. Four white-background covers were edited from actual product photos with image generation; the other selected covers are existing product images. Original private files remain intact. A new cover is appended when there is space; at the 12-photo limit, its source gallery reference is replaced and the original key is retained in the audit. No variants, money, reservations, inventory, order snapshots or financial history are modified. Preview targets and `SKIP_DEPLOY_DB_SETUP` keep their existing database-preparation guard.

Money is integer minor units (qəpik), bounded at input. Each item snapshots unit selling price, cost, product label, SKU and commission rule. Checkout runs a serializable transaction with retry, validates active products/variants and stock, creates a 30-minute reservation and a unique order/idempotency record. Expired reservations are released transactionally during checkout and admin order operations. Opening WhatsApp changes no payment/completion state. Confirming a live reservation commits the stock; confirming an expired reservation must reacquire availability. Cancellation releases reservations or restores committed stock. Returns restore committed stock once; physical return is whole-order in this first version. Payment/refund ledger is append-only; refunds do not imply goods were physically returned.

The default admin progress flow is **Təsdiqlə → Çatdırıldı**, available on each order row and in its detail. Explicit `deliver` actions accept confirmed/preparing/shipped orders only after stock has been deducted; they record actual delivery without inventing preparation/shipping history. A shared transactional helper completes a delivered order only when inventory is deducted and net recorded payment covers its total. It runs after explicit delivery, legacy delivery transitions and successful payments. The last actual payment on an already delivered order therefore completes it automatically. Legacy delivered/paid orders can still complete in one explicit click. Completion, eligible commission creation, hold date, one notification and completion audit occur atomically; retries do not create extra sales/payments/commissions or reset completion/hold dates. Generic direct status skips remain blocked, and closed/returned orders cannot be delivered again. Payment/refund/payout rules and snapshotted commission/minimum rules are preserved. Cancel/return and optional detailed shipping transitions remain under the secondary status controls. This flow never marks existing production orders delivered merely by deploying or reading them.

## Referrals, commissions and payouts

Referral signing prefers the independently configured `REFERRAL_SECRET`, preserving existing signatures. When it is unset or blank, a domain-separated HMAC key is derived server-side from `BETTER_AUTH_SECRET` (at least 32 non-padding characters). No default or browser-provided key is accepted. If neither is usable, capture returns a controlled 503 without recording a referral visit. Signing occurs before the visit write. Expiry, HttpOnly/SameSite/Secure cookie behavior, active-partner validation and order attribution rules remain unchanged. Rotating the effective signing key invalidates browser attribution cookies; historical orders retain their stored attribution. Browser acceptance also runs the full referral/order/commission/payout workflow with the optional referral secret absent.

Codes normalize to uppercase and are unique. HMAC-signed HttpOnly cookie records verified latest referral and expiry. Manual verified code takes priority, explicit empty checkout code clears attribution. Order attribution and commission policy are immutable snapshots. Completion requires delivered goods and full net payment. One commission per order. Approval checks hold, then transitions pending → approved → payable. Payout atomically claims exact payable commission IDs and immutable allocations; paid records remain intact. Cancellation/return/refund reverses unpaid commission; a paid commission gets an immutable negative adjustment. Payout can explicitly settle outstanding adjustments with a partner's next commissions, never silently overwrite history. Admin attribution corrections are permitted only before completion/commission and are audited; financial corrections require the documented dispute workflow.

## Security and integrations

The runtime reuses a process-wide Prisma client in production as well as development. PostgreSQL pools default to one connection per worker with a one-second idle timeout and allow idle event-loop exit. On Vercel, the official attachDatabasePool helper registers work after a request so its idle timeout runs before suspension; an ordinary idle timer alone can freeze and leave database sessions open. A small PrismaPg subclass attaches each internally created pool, retaining normal disconnect/reconnect disposal; Node Proxy attaches its separate pg pool without importing Prisma. The SDK's dedicated db-connections export avoids loading unrelated platform/auth helpers.

For the exact documented Prisma Postgres direct hostname db.prisma.io on the standard PostgreSQL port, application connections use pooled.db.prisma.io with the same credentials, path, query and TLS settings. Other providers and explicit endpoints are preserved. The original environment is not mutated: the migration runner continues using its direct DATABASE_URL and session advisory lock. Application advisory locks are transaction-scoped and compatible with transaction pooling. Node Proxy keeps client query/connection deadlines but avoids session-only statement_timeout startup parameters. Store-settings memoization remains request-scoped; no stale settings fallback or catalog/financial data rewrite is introduced. Provider plan/replica connection budgets still bound overall capacity.

Zod schemas reject malformed inputs. Mutations require trusted Origin (except authenticated job endpoint), JSON content type, and persistent rate limits. Better Auth manages password hashing/session cookies and login CSRF protection. Uploads require admin, bounded multipart input (including absent/incorrect Content-Length), a 4 MiB file limit and actual image decoding/reencoding. A private S3-compatible bucket or private Vercel Blob store holds image bytes; both serve through the same authorization-checked media route. A Blob store ID selects the provider; the official SDK authenticates each operation using trusted Vercel request-context OIDC or an existing read-write token. No SVG uploads or public Blob writes. CSV cells are protected from spreadsheet formula injection. Logs do not include secrets or request/customer payloads. Google Sheets is optional; outbox records update the same order row through an idempotent authenticated server integration. It never blocks order creation.

## Production requirements

Managed PostgreSQL, persistent private object storage (S3-compatible or Vercel Blob), TLS domain, cryptographic auth/referral/job secrets, configured WhatsApp number and first admin. Docker Compose supplies local PostgreSQL and object storage only. No payment gateway, automated banking, email, SMS or outbound WhatsApp messaging is implied. Tax accounting, partial merchandise returns and disputes involving already-completed attribution require explicit operational review; contribution is not full accounting net profit.
